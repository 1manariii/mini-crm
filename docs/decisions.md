# Решения и допущения

Что я решил сам там, где ТЗ допускает разные трактовки.

## Роли и пользователи

- Роль хранится в таблице `profiles` (`manager` / `executor`), привязанной к `auth.users`.
  Профиль создаётся триггером при создании пользователя; роль и имя берутся из user metadata
  (при создании пользователя в дашборде Supabase). Если роль в метаданных не указана —
  по умолчанию `executor` (меньше прав, безопаснее).
- Тестовые пользователи создаются вручную в дашборде, открытая регистрация отключена —
  как требует ТЗ. В обычном продукте сюда просится экран управления пользователями.

## Права доступа

- Исполнитель не имеет update-прав на таблицу задач вообще: его переходы статуса идут
  только через функцию `change_task_status()`. Постановщик может редактировать поля задачи
  напрямую, но сменить статус напрямую не может — это блокирует триггер, чтобы история
  всегда оставалась полной.
- Профили (имя и роль) читают все авторизованные пользователи. Иначе постановщик не смог бы
  выбрать исполнителя, а в истории не отображались бы имена. Утечкой в рамках внутренней
  CRM это не считаю: email и служебные данные в `profiles` не хранятся.
- Удаление объекта каскадно удаляет его задачи и историю (так ТЗ не противоречит,
  а «висячих» задач без объекта быть не должно). Удалять может только постановщик.

## Статусы и история

- В базе статусы хранятся английскими enum-значениями (`new`, `in_work`, …), русские подписи —
  только в интерфейсе.
- Матрица переходов продублирована на клиенте, но исключительно для того, чтобы показать
  доступные кнопки. Источник истины — функция в базе; ручной запрос с запрещённым переходом
  отклоняется.
- Комментарий обязателен только при возврате на доработку (по ТЗ). Функция в базе
  принимает комментарий и для других переходов, но в интерфейсе поле комментария есть
  только у доработки.
- Запись о создании задачи тоже попадает в историю (переход «из ничего» в «Новая») —
  так история отражает весь жизненный цикл, включая автора.

## Интерфейс

- «Мои задачи» показывается только исполнителю (по ТЗ экран для него); у постановщика
  полная картина видна через объекты.
- Дизайн осознанно простой: ТЗ просит аккуратный и понятный интерфейс, оценивается логика.

## Что не успел / осознанно не делал (объём ТЗ — 2–3 часа)

- Нет полнотекстового поиска, пагинации, фильтров по исполнителю и комментариев к задаче
  вне истории статусов.
- Нет realtime-обновлений списка (Supabase Realtime): данные обновляются при переходах
  и перезагрузке.
- Нет e2e-тестов: ручная проверка сценариев по двум ролям.
